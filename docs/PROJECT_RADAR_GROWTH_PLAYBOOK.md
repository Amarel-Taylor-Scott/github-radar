# Project Radar growth playbook

Project Radar should grow through usefulness, transparency, and repeatable distribution—not artificial engagement or undisclosed placement.

## Product surfaces

The central engine should produce several synchronized public surfaces from one validated snapshot:

- concise GitHub README leaderboards;
- searchable static catalog pages;
- permanent project evidence cards;
- Atom, RSS, and JSON feeds;
- daily change reports;
- weekly projects-to-watch reports;
- monthly domain trend reviews;
- machine-readable JSON, SQLite, and Parquet snapshots;
- thin standalone mirror repositories;
- social-preview cards generated from measured facts.

Every surface must declare the source commit, generation timestamp, schema version, and checksum.

## Star-worthy repository design

Each public mirror should immediately answer:

1. What does this list cover?
2. What changed today or this week?
3. Why did each project surface?
4. Which evidence is measured and which is provisional?
5. How can the data be consumed programmatically?
6. How can a project be nominated or corrected?
7. How is gaming prevented?

Recommended top-of-README elements:

- one-sentence value proposition;
- freshness and workflow badges;
- project and catalog counts;
- top five current projects;
- daily or weekly movers;
- links to searchable pages and feeds;
- transparent methodology;
- correction and nomination links.

## Repeatable editorial products

Generate from the normalized dataset:

- **Five projects to watch this week** — high-confidence momentum plus quality and diversity;
- **New projects before they become obvious** — novelty and under-recognition with minimum evidence thresholds;
- **Domain movers** — one project per catalog with the strongest observed weekly change;
- **Hidden infrastructure** — high-quality dependencies or developer tools with low catalog-local popularity;
- **Maintainer momentum** — only after a privacy-reviewed public-activity methodology exists;
- **Release watch** — notable new versions and release cadence changes;
- **Open-source category maps** — graph views of projects, packages, dependencies, and use cases.

Generated prose must distinguish facts from interpretation and retain source provenance.

## Search visibility

Static publication should include:

- one indexable HTML page per catalog;
- one page per project;
- canonical links;
- sitemap;
- JSON-LD metadata;
- Open Graph metadata;
- descriptive page titles and summaries;
- internal links among related projects and catalogs;
- permanent dated snapshots;
- no hidden keyword stuffing or duplicated low-value pages.

## Community loop

Support three structured contributions:

- project nominations;
- factual corrections;
- methodology proposals with benchmark evidence.

Do not use open-ended popularity voting as a ranking factor. It is easily gamed and duplicates GitHub stars.

Publish contributor acknowledgements for accepted factual improvements while preserving conflict-of-interest disclosures.

## Distribution cadence

### Daily

- regenerate catalogs;
- publish changes and one-day movers;
- update feeds and badges;
- create a short social-ready factual digest only when meaningful changes exist.

### Weekly

- publish projects to watch;
- publish new and under-recognized projects by domain;
- summarize source health and measurement maturity;
- create issue or release notes for major methodology changes.

### Monthly

- publish category growth and concentration trends;
- review false positives and correction requests;
- benchmark ranking stability and diversity;
- add or retire catalogs based on evidence.

## Ethical monetization options

Potential revenue should remain separate from ranking:

- paid API tiers for higher request volume;
- historical analytical datasets;
- enterprise watchlists and alerts;
- white-label domain radars;
- internal open-source intelligence dashboards;
- custom catalog configuration and deployment;
- sponsorship clearly separated from editorial ranking;
- consulting around project discovery, ecosystem mapping, and technology scouting.

Sponsored projects must never receive a ranking boost. Any commercial relationship should be disclosed on the relevant surface.

## Metrics that matter

Track product health rather than vanity alone:

- returning readers;
- feed subscribers;
- API and dataset consumers;
- citations and backlinks;
- accepted corrections;
- nomination precision;
- search-to-project click-through rate;
- weekly digest retention;
- ranking stability;
- catalog coverage and diversity;
- false-positive and stale-project rates;
- cost per successful daily publication.

Repository stars are useful, but they should not be the sole success metric for Project Radar itself.
